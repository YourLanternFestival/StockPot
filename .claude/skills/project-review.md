# 审查 Skill：数据管线审查

每次改动后，必须按以下流程自审。不是找代码 bug，是验证数据从输入到输出的完整路径。

---

## 第一步：读 schema

在做任何审查之前，先读 `db.js` 中相关表的字段定义：

```
找到 addXxx / getXxx / updateXxx 函数，列出实际字段名和类型。
```

**铁律：代码中引用的字段名必须和 db.js 完全一致。`order_date` ≠ `receive_date` 这种错误不能再犯。**

---

## 第二步：走数据路径

对每个涉及数据读写的改动，追踪以下路径：

```
用户输入 → 保存（写入哪里？DOM 还是 DB？） → 加载（从哪里读？） → 导出（从哪里读？）
```

每一步标注：
- 数据源：DOM / DB / 内存变量
- 字段名：是否和 db.js 一致
- 触发条件：什么操作触发这一步（点击按钮 / 切换样式 / 自动保存？）

**断点检测：如果保存写 DB 但导出读 DOM，就是断点。必须修复。**

---

## 第三步：模拟用户的完整操作场景

不要审"功能"，审"场景"。至少模拟以下场景：

### 场景 A：新功能的完整路径
1. 用户打开页面
2. 输入数据
3. 切换到其他页面再切回来
4. 点保存
5. 关闭再打开
6. 点导出，打开导出文件验证

### 场景 B：模式/样式切换
1. 在模式 A 输入数据但不保存
2. 切换到模式 B
3. 切回模式 A
4. 数据是否还在？

### 场景 C：跨模块数据流
1. 在模块 A 写入数据
2. 在模块 B 读取数据
3. 字段名、数据格式是否一致？

---

## 第四步：对照已有功能

如果是新增功能（如矩阵模式），必须对比已有功能（如样式1）的实现：

```
已有功能：save → load → export 的路径是什么？
新功能：save → load → export 的路径是什么？
两者是否一致？不一致的地方是否合理？
```

**铁律：新功能复用已有数据流，不要建割裂的独立系统。**

---

## 第五步：自问清单

审查完成后，逐条回答以下问题。任何一条答不上来或答案不确定，就是遗漏：

1. 数据保存到哪里？字段名和 db.js 一致吗？
2. 数据从哪里加载？读的是 DOM 还是 DB？
3. 导出从哪里读数据？如果用户在新功能里输入但没点保存，导出能读到吗？
4. 切换模式/样式时，数据会不会丢失？丢失的根因是什么？
5. 新功能的数据流和已有功能一致吗？不一致的地方有没有正当理由？
6. 用户误操作（快速切换、连续点击）会不会导致数据错乱？
7. 数据库字段名有没有用错（order_date vs receive_date 这种）？
8. 有没有遗漏的边界情况（空数据、多日期、多分页）？

---
